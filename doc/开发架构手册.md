# 本地 ArNS Gateway 开发架构手册

## 1. 项目目标

本项目实现一个轻量、可审计的本地 ArNS Gateway：自己读取 Solana 上的 ArNS/ANT 状态，自己解析 Arweave Path Manifest，优先从普通 Arweave 节点按 Chunk 提取 ANS-104 Data Item，并将不可变对象永久保存在本地。

它不是完整 Solana RPC、Arweave 节点或全量 Bundle Indexer。首次发现数据仍使用外部 RPC/索引，已镜像内容则可本地服务。

## 2. 组件视图

```text
浏览器
  │ HTTP: <arns>.localhost
  ▼
Native Gateway
  ├─ Input/Host normalization
  ├─ NativeArnsResolver
  │    └─ SolanaRpcPool：方法级健康、短缓存、有限 BFS
  ├─ 可选网页只读 RPC 桥接 ── 同一个 SolanaRpcPool
  ├─ Manifest router
  └─ ImmutableContentStore
       ├─ 本地 .data/objects
       ├─ BundlePeerSource
       │    ├─ 多个 GraphQL Bundle index
       │    └─ ArweavePeerPool /offset + /chunk
       │         └─ seed + 持久快照 + /peers BFS
       └─ raw Data ID providers（最后兜底）
```

## 3. 模块职责

### `src/server.js`

加载配置并选择运行模式：`native` 是默认原生模式，`proxy` 是旧版整站 Gateway 代理兼容模式。

### `src/config.js`

集中解析进程环境变量，将逗号分隔的 RPC、索引和 Peer 转为有序数组。配置只从当前进程读取，不写系统环境或用户配置。

### `src/arns.js`

负责输入规范化和本地域名提取，防止不安全主机名进入解析流程。

### `src/native/arns-resolver.js`

解析链路：

```text
name/undername
  -> ARIO.getArNSRecord(baseName)
  -> ANT.init(processId)
  -> ANT.getRecord(undername)
  -> targetId, targetProtocol, ttlSeconds
```

经 SDK 自定义 transport 调用共享 SolanaRpcPool，保留 64 位整数精度。成功解析持久化到 `.data/resolutions`；TTL 到期后刷新；全部 RPC 失败时可使用 stale 记录。失败后有 30 秒内存退避，并合并同一名称和刷新模式的在途解析，避免页面资源重复等待离线 RPC。强制刷新不被普通缓存请求吞掉；确认不存在的名称返回 404，不使用过期映射冒充现存记录。

### `src/native/solana-rpc-pool.js` 与 `rpc-bridge.js`

池按方法跟踪可用性，限流时让整个端点冷却，其他错误对方法退避；相同请求合并，成功结果短缓存 2 秒。候选耗尽后通过 `getClusterNodes.rpc` 有限 BFS，过滤非公网地址并比较 genesis hash。新节点边发现边用于请求，发现有独立的数量、深度和超时上限。

可选桥接脚本在 HTTP HTML 响应中注入，不改变永久对象；仅将名单内主机的受支持只读 `window.fetch` 请求交给同源本地接口。默认只启用 Cyberleek，不接管交易发送、钱包或其他链。完整策略与边界见 [缓存与 RPC 池](缓存与RPC池.md)。

### `src/native/content-store.js`

以 43 字符 Data ID 为 key：

```text
.data/objects/<id>.body
.data/objects/<id>.json
```

读取顺序：

```text
本地对象 -> BundlePeerSource -> raw provider 列表
```

Data ID 对应的对象不可变，因此对象没有 TTL。同一实例中相同 Data ID 的并发请求合并为一次下载。写入使用唯一临时文件加原子 rename，避免进程中断留下半个对象；正文与元数据是两个独立文件，并非跨文件事务。

### `src/native/content-encoding.js` 与 `retry-read.js`

链上文件可以带有 Content-Encoding 标签。路由 Manifest 和提供 HTTP 响应前按标签解码 gzip、deflate 或 Brotli，并限制解压后的尺寸；磁盘保留原始字节，避免改变不可变对象。旧缓存缺少 encoding 响应头时可以从已有 tags 恢复。重新计算响应长度与 ETag，不沿用原始压缩字节的摘要。

GraphQL 定位和可选 raw provider 的幂等读取，遇到瞬时网络错误或可重试 5xx 时最多增加一次重试；401、403、404、429 和证书错误不盲目重试。

### `src/native/bundle-peer-source.js`

负责 Bundle 定位与选择性提取：

1. GraphQL 查询 `bundledIn`，取得直接父 Bundle ID。
2. 从健康 peer 池取得 `/tx/<parent>/offset`；offset 节点与数据节点不必相同。
3. 根据交易 end offset 和 size 计算起点。
4. 通过 `/chunk/<absoluteOffset>` 跨节点分批重试，读取 Bundle 前 32 字节。
5. 取得 item 数量 `N`，再读取 `32 + N * 64` 字节索引头。
6. 扫描 size/ID entries，计算目标 item 的绝对起点和大小。
7. 只读取覆盖该 item 的 Chunk。
8. 解析签名类型、owner、target、anchor、Avro tags 和 data。
9. 验证 `Data ID == SHA-256(signature)`，再把正文交给对象库。

Bundle 索引在进程内按父交易缓存。不会把完整父 Bundle 写入磁盘。

普通非 Bundle L1 交易也使用 `/tx/<id>/offset` 加跨节点 `/chunk` 读取，不再强制使用 raw Gateway。每批 peer 请求取第一个成功结果并取消剩余请求，不等待最慢节点；取消不记为节点失败。读取响应正文期间仍受超时约束。

### `src/native/peer-pool.js`

维护普通 Arweave 节点的持久快照：

1. `ARWEAVE_PEERS` 是固定 seed。
2. 首次及定期刷新从 seed 加旧快照开始 BFS 请求 `/peers`。
3. 地址去重并过滤回环、私网、链路本地和保留地址。
4. 成功率、失败次数和延迟用于候选排序。
5. 刷新成功后删除本轮既不可访问、也没有被活节点再次提到的旧地址；整轮断网时不清空快照。
6. 当前 Chunk 失败时只做逐层即时发现，边发现边重试；完整 BFS 在后台构建快照。

节点快照位于 `.data/peer-pool.json`，默认每 6 小时更新一次。

### `src/native/manifest.js`

识别 Arweave Path Manifest，实现根路径 index、精确 paths 映射、目录 `index.html`、fallback 和全站 Data ID 枚举。

### `src/native/gateway.js`

组合上述服务并返回 HTTP：首页、`/open`、`/api/status`、`/api/resolve`、`<name>.localhost` 内容、Manifest 路由和诊断响应头。

### `src/mirror.js`

强制刷新 ArNS 解析，然后下载 Target Manifest 与其中全部唯一路径 Data ID，用于离线预热。

### `src/check-endpoints.js`

检查 Solana RPC 的时隙、账户读取和程序扫描能力，以及 Bundle GraphQL 和 Arweave Peer 的基本健康状态。只读，不修改系统或远端状态。

## 4. 通用 ArNS 网站请求时序

```text
Browser          Gateway        Solana RPC       Bundle Index       Arweave Peer       Local Store
   | GET /          |                |                  |                  |                  |
   |--------------->|                |                  |                  |                  |
   |                | resolve name   |                  |                  |                  |
   |                |--------------->|                  |                  |                  |
   |                | target + TTL   |                  |                  |                  |
   |                |<---------------|                  |                  |                  |
   |                | lookup Target -------------------------------------------------------->|
   |                | cache miss <-----------------------------------------------------------|
   |                | bundledIn? ---------------------->|                  |                  |
   |                | parent ID <-----------------------|                  |                  |
   |                | /tx/id/offset + /chunk ---------------------------->|                  |
   |                | selected item bytes <-------------------------------|                  |
   |                | verify + store ------------------------------------------------------->|
   |                | parse manifest, map / -> index.html                                   |
   |                | lookup index Data ID ------------------------------------------------>|
   | HTML <----------------------------------------------------------------------------------|
```

随后浏览器请求 JS、图片和 favicon；解析记录在 TTL 内有效时，Manifest 和文件可直接从本地返回。接入桥接的网页业务 RPC 经共享池读取，其余请求仍由网页自行访问外部服务。

## 5. 缓存模型

可变层：

```text
ArNS name -> targetId
```

必须遵守 ANT TTL。其缓存目的是减少 RPC 压力和支持临时离线，而不是永久冻结名称。

不可变层：

```text
Data ID -> bytes
```

对象永久缓存，不按时间失效。ArNS 指向新 Target 时新增对象，不覆盖旧对象。

浏览器看到的名称路径不是不可变 Data ID，必须向本地服务重验证。HTTP ETag 包含当前 Target 与实际响应字节，先解析名称再决定 304。过期解析 fallback 标记 `no-store`；动态 RPC 仅用 2 秒内存缓存，不写入永久对象库。

## 6. 故障切换

```text
Solana RPC 方法级候选 -> 冷却/切换 -> 有限 BFS 新候选 -> stale ArNS resolution
Bundle Index A -> B
Arweave seed/旧快照 -> offset 节点 -> 每个 Chunk 跨 peer 重试 -> 失败时逐层 BFS
Native bundle extraction -> raw provider A -> B -> C
```

故障切换解决可用性，不等于共识验证。当前解析取第一个成功结果，并未比较多个 RPC 的账户值。

## 7. 安全与信任边界

已经具备：

- 名称和 Data ID 格式验证。
- Manifest 路径清理。
- 响应大小限制和请求超时。
- Bundle item ID 与签名哈希核对。
- Bundle 总尺寸一致性检查。
- raw 响应声明 ID 和 `Content-Digest` 检查（服务商提供时）。
- 本地对象原子写入。

尚未完成：

- 完整 Data Item 公钥签名验证。
- Arweave `data_path` / `tx_path` Merkle proof 验证并锚定可信区块头。
- 多 Solana RPC 结果 quorum 比较。
- Bundle 索引结果持久化。
- 嵌套 Bundle 的递归选择性读取。
- Solana RPC 节点的独立真实性验证和 quorum。
- 网页 Web Worker、WebSocket、XHR 等请求的 RPC 桥接。

因此错误索引通常会导致找不到或失败，而不会直接被当成正确对象；但在完成签名和 Merkle proof 验证前，不能把当前实现描述为完全 trustless。

## 8. 存储与资源模型

- 代码约百 KiB。
- npm 依赖约几十 MiB。
- Bundle 只保留目标对象，不保留完整父交易。
- `.data` 随实际访问的不可变文件总大小增长。
- 运行期 Bundle 索引和响应 Buffer 会短暂占用内存；单对象受 `MAX_RESPONSE_MB` 限制。

## 9. 扩展顺序建议

1. 扩展方法级 RPC 诊断及 quorum 验证。
2. 持久化 `Data ID -> root transaction + item offset + size`。
3. 验证 Chunk Merkle proof 与 Data Item 签名。
4. 支持 offsets RPC，跳过本地 O(N) Bundle header 扫描。
5. 支持嵌套 Bundle。
6. 增加流式响应，避免大对象全部进入内存。
7. 为多进程并发写入增加对象级锁。

## 10. 测试策略

当前 `node --test` 覆盖 ArNS 输入规范化、磁盘缓存、ANS-104 Data Item 解析和 ID 核对、Manifest 路由、并发对象下载合并、首个成功 peer、内容解码和尺寸限制，以及 RPC 方法级切换、429 冷却、缓存/合并、BFS/网络过滤、TTL/stale、强制刷新、HTTP 304/404 和只读桥接。

涉及外部网络的验证应单独运行 `npm run check:endpoints` 和 `npm run mirror -- <name>`，避免把不稳定公共服务放入确定性单元测试。

实站冷启动结果见 [兼容性测试](兼容性测试.md)，不以首页 HTTP 200 代替应用渲染或业务验证。
